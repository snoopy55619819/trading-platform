Trading Platform: current plan (MVP)

What we are building through milestone 8, with the merges we made to keep scope manageable: the broker is one backend process, the exchange is one binary. Components tagged BUILT exist today; every other box carries the milestone that builds it.

Key

  • Order plane: private, request/response
  • Market data plane: public broadcast
  • Library linked in
  • Deployable process
  • Module inside one process
  • Library
  • Datastore
  • Company boundary
  • M1-M8: milestone that builds it

Legend

#ElementWhat it does
1webStatic bundle, not a server. Calls backend for orders and positions, market-data for prices, and joins the two itself, so the backend has no market data dependency.
2backendOne process, four modules: api (auth, no business logic), oms (pre-trade risk and order lifecycle), ledger (double-entry books), fix (session to the exchange). Merged because a buying-power check and the order write must be one transaction. Single instance: a FIX session is a stateful singleton.
3broker-dbBuilt. Holds the security master today; orders and the ledger land here at M5-M6.
4Order (edge)FIX 4.4 over TCP. The broker is the initiator (TypeScript), the exchange the acceptor (Rust): two independent implementations sharing only the dictionary.
5gatewayBuilt (M2). The exchange's door. Session sequence numbers, then tick size, lot size, price band and duplicate ClOrdID checks before the engine sees anything. Conformance-tested against QuickFIX/Go, including a SIGKILL and recovery by resend.
6exchange-dbBuilt (M2). FIX session state, so sequence numbers survive a restart. The exchange's own database, never a schema in the broker's.
7fix-coreBuilt (M2). Library, not a server: FIX codec, data dictionary and session state machine. Has never heard of an order book.
8matching-engineBuilt (M1). The market: price-time priority over an in-memory book, about 0.2 µs per match at the median. Feeds both planes, so it straddles the divider.
9journalBuilt (M1). Append-only log, written before each command is applied. Recovery is replay, which rebuilds a byte-identical book; a torn final write from a crash is dropped safely.
10ExecutionReport (edge)The private result: account, client order id, fill qty and price, fees. Goes only to the order's owner.
11md-publisherBroadcasts book changes to every subscriber. Never learns whose order moved the book.
12Feed (edge)Snapshot, BookDelta, TradePrint, Heartbeat, each stamped with feed_seq. A gap means lost data: resync from a snapshot.
13market-dataThe broker's market data service: live fanout to web and chart history. Its own database (md-db), separate because the workload is different, not because of an org chart.
14simulatorSynthetic trading firms that keep the book alive 24/7. Uses the same public FIX gateway and feed as everyone else: no backdoor.

Not shown on purpose: ExecutionReports back to the simulator (same shape as #10), and per-service migrations. Cut from the MVP entirely: a second venue, smart order routing, the consolidated tape, and all of post-trade (clearing, custody, settlement). See the ideal end-state diagram.
